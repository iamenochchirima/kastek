## Outcome and rules

Finish with Growth Core, Agency's Tenant backend and Labs Analytics running as TypeScript services. Preserve their implemented functionality, public and internal contracts, permissions, database behavior and background work. Their existing frontends and service consumers must work with the replacements.

The language migration is complete only after the TypeScript implementations run locally, parity evidence is recorded, local launch/build references use TypeScript, and replaced Rust code and build artifacts are removed. A successful compile or a collection of placeholder routes is insufficient. Hosted Railway settings, cutover and deployment are excluded from this completion gate by the owner's direction.

- Work one service at a time: shared foundation, Growth, Agency, Analytics, final shared-library retirement.
- Keep Growth on `rewrite` and Labs on `main`. Record Agency's existing working branch before implementation. Do not create additional branches, repos, issues or automated tasks by default.
- Implementation is authorized. Do not change hosted service settings or deploy as part of this migration.
- Keep PostgreSQL, the service boundaries, existing API/event versions and current UIs. Keep Keycloak, the Collector and existing TypeScript Agents services.
- Use native local processes. Do not use Docker without the owner's permission.
- Preserve current database contents and integration configuration. This is a fresh product; no historical account conversion, dual-login flow or general legacy compatibility layer is required.
- Rust and TypeScript may coexist temporarily for comparison. They must not both consume a real queue, execute schedules, send mail, charge accounts or publish the same effects.
- Preserve behavior that exists in code. Record incomplete behavior honestly. Do not implement unfinished roadmap features or remove existing functionality under cover of this migration.
- Keep checks focused, reusable and proportional to risk. Reuse fixtures and existing meaningful tests instead of building a second large test system.

## Target implementation

These are migration defaults to use consistently, subject to checking compatibility during phase 1. They do not justify unrelated rewrites.

| Concern | Direction |
| --- | --- |
| Runtime and tooling | One supported Node release across services, target Node 24; pnpm, strict TypeScript, `tsx` for development, compiled JavaScript for production, lockfiles |
| HTTP | Fastify 5, following the existing Agents conventions; keep each service's paths, status codes, response/error shapes and transport behavior |
| PostgreSQL | `pg` pools and explicit parameterized SQL/transactions, preserving existing SQL and ownership boundaries |
| Schema ownership | Keep Growth's existing Prisma schema/migration ownership; keep Agency/Analytics SQL migrations. Do not introduce a new ORM or duplicate schema authority |
| Validation | Runtime schemas at trust boundaries; retain existing JSON Schema contracts and their validation semantics. TypeScript types alone do not validate requests |
| Identity | Maintained OIDC/JWT/WebAuthn-related libraries; Keycloak remains responsible for account methods. No custom token verifier or password implementation |
| Telemetry | Structured logging and OpenTelemetry, reusing the Agents conventions and keeping current service identities |
| Workers | Separate executable commands where currently supported, with shared service modules; retain leases, retry rules and graceful shutdown |
| Shared delivery | Small private versioned Labs packages. Proposed split: browser-safe contracts and server-only support. Exact private registry/access setup is verified in phase 1 |
| Source layout | Keep each service's current owner and folder. Place temporary TypeScript source beside Rust during the port; retire replaced `.rs` files only at its deletion gate |

Growth-specific actions/execution remain Growth-owned. Share only contracts or generic helpers with real cross-product consumers. Do not translate eight crates into eight npm packages automatically.

Use Node's standard crypto or established libraries where appropriate, preserving algorithm, key derivation, encoding, ciphertext envelopes and associated data. Do not invent cryptographic primitives. Keep server secrets out of browser-safe packages.
